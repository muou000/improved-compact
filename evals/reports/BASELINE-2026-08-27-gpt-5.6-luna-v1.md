# DSH 原生上下文压缩真实模型基线：gpt-5.6-luna

## 决策

使用 DSH 当前配置的 `openai/gpt-5.6-luna` 建立 `compaction-basic` 加默认 `tool-result-pruner` 的真实模型基线。本报告只固定基线，不进行候选策略晋级判断。

5 次重复运行共执行 20 个案例、25 次原生压缩摘要和 20 次压缩后结构化问答。所有调用均成功，所有结构门槛均通过；压缩后的后续任务 micro 成功率为 `38/50 = 76.00%`。最明确的策略缺陷仍是长工具结果中部事实丢失：`hidden_nonce` 在 `0/5` 次问答中被恢复。

## 基线、数据与环境

- DSH commit：`b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`，运行时上游工作区干净。
- 模型：DSH settings 与 credentials service 解析出的 `openai/gpt-5.6-luna`，配置上下文窗口 `272000`。
- 数据集：`dsh-native-compaction-baseline-v1`，4 个合成案例，重复 5 次。
- 数据集 SHA-256：`41376db5d50cf5fc6750427568736c7272128940f154fdbbc79cb381801cbfcd`。
- runner SHA-256：`8f6f59737fec2c765211873702c3784ccb43300ba41707370aea41228dbcb253`。
- scorer SHA-256：`fe5f056b987fa0403d0cf713a00e6a7e81c2b1a79b84aea45a08e9cd5ebd27fb`。
- 运行环境：Windows x64，Node.js `v22.20.0`。

配置模型的真实上下文窗口远大于当前合成 fixture。为避免构造接近 272k tokens 的非代表性输入，评测将案例压力阈值设为 `1200/2400` estimated tokens，同时保留原合成案例的 `192/384` token 保留预算。原生八段摘要提示、区域选择、默认工具裁剪、压缩事务、session log、token meter 和模型路由均保持不变。

压缩完成后，评测器仅把压缩后的模型可见 surface 交给同一个 Luna，并要求按固定 JSON schema 回答案例问题；期望答案不会写入提示。评测器不为原生摘要调用增加额外重试，也不从统计中删除调用失败。

## 聚合结果

| 指标 | 结果 |
| --- | ---: |
| 压缩成功率 | `20/20 = 100%` |
| 压缩后问答调用成功率 | `20/20 = 100%` |
| 后续任务成功率，micro | `38/50 = 76.00%` |
| 后续任务成功率，macro | `75.83%` |
| 精确字面锚点召回，micro | `2/22 = 9.09%` |
| 精确字面锚点召回，macro | `10.00%` |
| estimated token 节省，macro | `59.08%` |
| session log 重放、no-op、工具配对与调用契约 | 全部通过 |

精确字面锚点召回只接受原文片段，忠实改写也会记为 miss，因此它是保守的诊断指标，不能单独代表摘要质量。任务层结构化问答更接近实际可用性；两者需要同时保留，才能区分“措辞变化”和“事实无法用于后续任务”。

## 逐案例结果

| 案例 | 压缩成功 | 后续任务 | 平均 token 节省 | 关键观察 |
| --- | ---: | ---: | ---: | --- |
| `continuity-core` | 5/5 | 12/15 = 80.00% | 60.25% | 目标文件和约束均为 5/5；下一步命令精确值为 2/5 |
| `correction-wins` | 5/5 | 10/10 = 100% | 64.28% | 新 region 和 rollback 均为 5/5，旧值未覆盖纠正 |
| `tool-prune-middle-loss` | 5/5 | 5/10 = 50.00% | 53.96% | 最新工具 pair 为 5/5；中部 `hidden_nonce` 为 0/5 |
| `repeat-compaction-drift` | 5/5 | 11/15 = 73.33% | 57.82% | 两次压缩均完成；最新 driver 5/5，迁移文件 2/5，下一命令 4/5 |

5 次运行的语义 digest 全部不同。这对概率模型是预期结果，不表示结构不稳定；每次运行的压缩次数、重放等价、压缩后立即 no-op、工具调用/结果配对和摘要调用契约仍全部通过。质量波动主要出现在需要保留精确命令或文件路径的检查上。

## 调用与延迟

| 调用类型 | 成功 | input tokens | output tokens | cache read tokens | 平均延迟 | P95 | 最大值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 原生压缩摘要 | 25/25 | 53,157 | 10,245 | 98,048 | 9.88 s | 13.17 s | 32.46 s |
| 压缩后问答 | 20/20 | 35,986 | 526 | 76,800 | 2.22 s | 2.80 s | 6.54 s |

单次完整 4 案例运行平均 `58.32 s`，标准差 `8.48 s`，范围 `51.67-74.26 s`。`cache read tokens` 按 provider usage 原样单列，不能与 input/output 简单相加为费用；本报告也不在缺少固定价格快照时推算成本。

一轮正式样本中 45/45 次调用成功。此前用于校准 runner 的 3 次诊断运行曾出现一次上游 `502` 和一次下游结束异常，但未计入本报告正式五次统计。这说明当前样本不足以证明服务稳定性，扩大运行次数时应继续同时报告无条件成功率和排除调用失败后的条件质量。

## 已知失败与改造信号

1. `tool-result-pruner` 在摘要前不可逆删除长工具输出中部。模型 5 次都无法恢复 `hidden_nonce`，而工具 pair 始终完整；这将“结构正确”和“事实保真”明确区分开，应作为首个候选策略的硬回归案例。
2. 摘要对精确命令和文件路径的保真不足。连续压缩后迁移文件只有 2/5 精确，下一命令为 4/5；`continuity-core` 的下一命令也只有 2/5 精确。候选策略应为文件、命令、错误文本和标识符提供明确的 verbatim 保留通道。
3. 后来纠正的状态表现稳定。`correction-wins` 达到 10/10，说明优化时不应以增加冗余为代价破坏“新事实覆盖旧事实”的能力。
4. 平均 token 节省约 59%，但不能脱离 76% 的任务成功率单独优化。后续 A/B 应以逐案例任务成功率为主要质量门槛，以 token、延迟和调用成功率作为共同约束。

## 未验证风险

- 本次没有发送接近模型真实 272k 上下文窗口的请求，因此不验证真实临界窗口下的延迟、截断和 overflow 恢复。
- 4 个案例是开发/验证集，不是不可见 holdout；不能用于反复调参后的最终晋级结论。
- 尚未覆盖真实编码任务的外部状态验证，例如压缩后继续修改文件并通过测试。
- 尚未覆盖多并行工具、图片、跨语言长文本、权限变化、摘要超时和损坏 session log。
- 5 次重复足以暴露明显的系统性失败，但不足以给小幅改进建立窄置信区间。

完整逐次 JSON 证据保存在被忽略的 `evals/.local/gpt-5.6-luna-baseline-final.json`，其中不包含凭据。
